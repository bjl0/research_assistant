STEP 1. Set up
Make a working folder RUN in your scratch space with a subfolder RUN/in. With ArtifactData action "get" on the dashboard url:
- collection "screener", doc "script": save its "text" field as screen.py (use out_dir to save the document as JSON, then extract "text" with a short python command).
- collection "dash", doc "params": save its data object as RUN/params.json.
- collection "screener", doc "profiles": save its data object as RUN/prev_profiles.json, and note its version.
- collection "datasets", docs "tokens" and "alerts": note each one's version and its source.url, which looks like /_blob/<id>.
Then call Artifact action "read" with the dashboard url and path = the alerts blob id (a single path, not paths), and copy the saved file to RUN/prev_alerts.json.

FETCHING RULES (use WebFetch; the shell cannot reach these sites)
- Every URL must carry a fresh random query value. The script adds ?z=xxxx to the URLs it prints; for the three list URLs in step 2 add your own ?z= value, different on every run. Without it the fetch can return a copy that is hours old.
- WebFetch answers through a small model. Always ask for extraction into the exact keys given below, never for the raw page. Save each answer exactly as returned into the named file with the Write tool.
- Send fetches in parallel batches. If one errors, retry it once with a new ?z= value, then skip it and mention it at the end.
- URLs longer than about 230 characters are rejected, which is why the script puts at most 4 tokens in one URL. Do not merge URLs.

STEP 2. Candidate lists
Fetch each of these with this prompt: For each item with chainId exactly "solana" output one line: tokenAddress, a space, then the timestamp number at the end of its openGraph URL. Copy addresses character for character. Skip duplicates. Nothing else.

STEP 3. Market data

Fetch every URL it prints with this prompt: Output a compact JSON array, one object per pair, with only these keys: mint (baseToken.address), sym (baseToken.symbol), name (baseToken.name), dex (dexId), pair (pairAddress), quote (quoteToken.symbol), liq (liquidity.usd or null), mc (marketCap or null), v24, v1 (volume.h24/h1), b24, s24, b1, s1 (txns buys and sells for h24/h1), pc24, pc1 (priceChange, null if missing), created (pairCreatedAt), ts (the timestamp number at the end of info.openGraph, null if none), boosts (boosts.active or 0), x (the url of the first info.socials entry whose type is "twitter", or null if there is none). Save the answers as RUN/in/market_01.json, RUN/in/market_02.json and so on.

STEP 5. Build, then wallet profiles
Run: python3 screen.py build RUN
It prints a run summary and up to 20 profile URLs. Fetch each with this prompt: Output one compact JSON object and nothing else: {"address": the address field, "username": the username field or null, "followers": the followers count or null}. If the page is an error or has no profile, output {"address": null, "username": null, "followers": null}.
Save the answers as RUN/in/profile_01.json and so on. When a profile fetch fails or returns a null address (usually the wallet has no profile), save {"address": "<the wallet address from that URL>", "username": null, "followers": null} instead, so it is not looked up again. Then run the build command once more. Ignore any profile lookups it still lists; later runs do them.

STEP 5b. Token images
After the last build, run: python3 screen.py images RUN
It downloads the alert tokens' thumbnails itself and adds them to RUN/out/alerts.json; do not use WebFetch for images. If it says downloads failed, carry on to step 6: thumbnails from earlier runs are kept, and this does not block the run. Do not try to get images any other way.
